## 2. 決定 + 経緯
- 本番を壊さないため、表示・管理機能は既存データを直接書き換えない overlay 方針を継続する。
- `data.enc` と `calendar.enc` は再生成しない。
- 退会は削除ではなく状態変更にする。
  - 過去トレーニング履歴は保持する。
- 顧客名を履歴の主キーにしない。
  - 安定した顧客ID + aliases で表示名変更に耐える。
- 自動同期先は個人用Google Driveにする。
- 公開GitHubへ顧客データ・個人Drive ID・非公開URL・認証情報を置かない。
- 同期データはブラウザ側で暗号化してから保存する方針。
- 同時更新で片方を消さないため、同期は「単純上書き」より「暗号化スナップショットを読み込み統合する方式」を優先する。
- 外部同期基盤を勝手に追加しない。
  - 現時点の静的GitHub Pagesだけでは安全な書き込み先がないため、Google Apps Script Web APIを別途用意する必要がある。

## 5. ハマり所
- GitHub Pagesは静的サイトなので、それ単体では顧客データの安全な書き込み先にならない。
- Google DriveコネクタはSheetsの作成・編集はできるが、Apps Scriptの新規作成・Webアプリデプロイはできない。
- Windows PCには `clasp` が入っておらず、`~/.clasprc.json` も存在しなかった。
- `axis_training_key` は「このiPhoneでコードを記憶」を有効にした場合のみlocalStorageにある。同期暗号化キー設計では、未記憶端末でもunlock中のアクセスコードを安全に扱える実装が必要。
- `axis_training_edits_v1` は編集時に `updatedAt` を持つが、復元でentry自体を削除するため、複数端末同期では「削除のtombstone」がない。自動同期時は復元操作の競合対策が必要。
- `axis_hidden_schedule_v1` は単純配列。複数端末同期で「非表示解除」を伝えるにはunionだけでは不足するため、将来的には更新履歴またはtombstone方式が必要。
- ローカル検証ではService Workerの古いキャッシュが新JS読込を邪魔したことがある。テスト時は新規プロファイルまたはSW無効でコード確認し、本番ではSW有効で再確認する。
- 公開リポジトリなので、個人DriveのファイルID、Apps Script URL、共有秘密、実顧客名をコミットしない。
